# 把变化接到当前项目

CF 发布了一个 SDK 方法，或者项目准备从本机移到 VPS，都可能改变技术选择。先找回“当前为什么这样做”，再检查新的条件，可以少做一轮重复选型。Fieldbook 提供通用机制和复查入口；项目的当前用法、采用理由与验收由项目持有。

本文的三个场景与输出均为合成示范，展示 agent 怎样带着依据继续工作，不声称重新验收了任何真实项目。复制[任务单](../templates/project-context-task.md)时，只补本次目标和目标 repo；能从文件查到的事实由 agent 自行取得。

## 当前采用理由放在哪里

优先接到项目已有的 architecture、runbook、决策文档或对应模块说明，不另建一份要人工同步的跨项目台账。

| 要留下什么 | 由谁持有、怎样取回 |
|---|---|
| 当前路线与它解决的问题 | 项目文档说明目标、约束和所选路径；限定成立范围 |
| 支撑路线的实现、config、dependency 与验收 | 项目持有；agent 给出路径／行号、版本或安全证据位置，区分源码与 runtime |
| 曾考虑的替代路线及暂缓原因 | 接在已有决策段落；不能只写一个无条件的“不要用” |
| 什么条件会改变选择 | 描述可观察条件，例如新增独立消费者、远端多步骤任务或成员登录需求 |
| 本书怎样解释机制 | 链接稳定内容 ID、repo 路径与小节；历史实践另标观察日期 |

例如项目已经记录“当前没有远端多步骤任务，因此暂缓 Workflows”，本次只改静态页面配色时，agent 可以复用这个判断。若后来出现远端任务、等待与失败恢复，再读[任务恢复](recoverable-jobs.md)并检查项目是否满足采用条件。不要把曾经缺少的需求写成永久产品禁令。

Fieldbook 不存项目真实账号、部署配置或跨 repo 当前状态。私人证据留在项目批准的位置；需要写回本书时，只提取可公开机制、匿名编辑后的观察和合成复现。历史[私有资料站实践](../practice/private-reader.md)解释过入口从 Access 转到应用成员 Session；它不能证明另一个项目今天仍用哪一种身份路线。

## 两种触发，走同一个判断过程

上游触发可以是 API 字段移除、SDK 返回类型变化、价格生效或新操作入口；项目触发可以是运行位置、用户数量、内容敏感度、发布时长或功能变化。项目自身变化不需要等上游发公告。

| 步骤 | agent 应取得的内容 | 交到下一步的结果 |
|---|---|---|
| 固定本次目标与变化 | 用户目标；官方依据、版本和生效日期，或项目的实际变化 | 哪条原有假设需要重看 |
| 取回当前判断 | 已有路线、理由、替代方案和重评条件 | 有依据的起点；冲突或缺失明确标出 |
| 查具体使用点 | 当前 dependency、调用、字段解析、config 与受影响流程 | 命中位置；或未发现的检查范围；或未知 |
| 取回相关机制 | 本书稳定条目与小节、来源、离线例子 | 只带本次任务需要的解释和验证方法 |
| 给出可继续工作的判断 | 条件是否改变，证据够不够，授权还差什么 | 沿用、重评或继续补证据，并接到一个具体下一步 |

源变化可先运行 `python3 tools/fieldbook.py impact-source S117`；内容变化使用 `impact <content-id>`。两者都是本书内的候选查询。找到了手册和参考页以后，仍须到项目核查调用，才知道项目是否受影响。[API 维护指南](../reference/api-maintenance.md)说明客户端行为和结果完整性。

## 三种适用性结果：命中、未发现、未知

**命中**需要位置和机制。例如某脚本读取 Tunnel list/get 的 `connections` 字段，而官方将它移除并给出专用查询路线；应说明哪个解析点受影响以及怎样验证改动。[S117]

**已查范围未发现**需要列出读过哪些 dependency、config 与调用路径，并说明覆盖限制。只知道项目用了 Tunnel，或者只搜索一次产品名，不能据此断言所有运行路径都不受影响。不要重复打扰 owner 处理没有命中的候选；保留可以复用的核查范围。

**未知**需要指出缺什么，以及最小补证据动作。源码中找不到调用，但部署里可能有独立脚本；真实运行资料不可访问；旧文档和当前 config 冲突，都属于需要继续核查的情形。访问权限、外部操作授权和 owner 意图各自处理，不能用猜测补齐。

“命中 API 变化”和“值得采用新服务”也分开。新 SDK 方法先提供接口证据；是否改善本次问题，要比较已有实现、开放条件、迁移与恢复成本，并取得相应实际验证。

## 场景一：已有阅读服务尽量搬到 VPS

目标是减少源设备的进程、内存与存储负担。先依据当前实现把采集或设备专属能力与可远端执行的阶段分开，再找现有部署判断。Tunnel 改访问路径；让进程和数据离开源设备还需要迁移方案、配置、恢复与验收。[手册入口章节](../guides/handbook.md#access)解释两种位置的职责。

可交付的合成工作上下文：

> 当前目标：减少源设备常驻负担。已读项目的部署说明、进程入口与数据目录声明；设备采集阶段暂留本机，后续处理是迁移候选。运行位置的原假设需要重评。先检查 VPS 的依赖、数据权限、连通与恢复，再做授权范围内的迁移。Workflows 只有出现远端多步骤任务时重开；检索和共享存储分别检查自己的条件，不随运行位置一起自动改选。

真实项目输出应把这段中的概括替换为实际路径、版本和覆盖范围；没有读取运行证据时明确标 `runtime 未验证`。

## 场景二：资料发布越来越慢

先定位发布链实际耗时：本地整理、对象上传、索引等待、读回核对、最终切换分别观察。撤下、版本与权限语义由项目负责，不因换 SDK 消失。[资料站实践](../practice/private-reader.md)解释交付原件、检索候选与回读之间的关系。

可交付的合成工作上下文：

> 当前只有“发布变慢”的报告，尚无阶段耗时证据。下一步在现有 publisher 的步骤边界取得安全的时间记录；不先迁移检索或换语言。若重复 API 编排、分页遗漏或客户端维护成本命中瓶颈，再比较现有语言的 SDK。上传成功、索引可见与正式版本切换各自验证，部分失败保留已完成范围。

这里的 SDK 是可能的改进材料；[可靠读取例子](../examples/api-operations/README.md)可帮助检查分页、期限与失败报告，却不能测量真实发布链的耗时。

## 场景三：独立静态产品官网继续美化

先核对当前产物是不是静态页面、部署路线和资源交付怎样组成。视觉编辑需要自己的页面验收。若没有新增表单、账号、受控下载或安装包分发需求，继续完成静态发布；这些具体需求出现时，再重开后端、身份或存储选择。不能从“也是 Cloudflare 项目”推导出要引入整套云端应用产品。

可交付的合成工作上下文：

> 当前改动只涉及静态页面布局和资源；已读站点源码与发布说明。沿用已有托管、域名与部署路线，验证桌面、手机和下载链接。暂缓后端路线的条件未变。若增加提交表单、成员资格或受控文件分发，再定位对应数据、权限与恢复问题。

## 怎样算减少了重复判断

这条路径应让 agent 自行找回已有取舍、指出具体变化是否命中，并带着证据继续工作。不要要求 owner 手填机器能读到的 dependency、字段和部署文件；只把无法取回的目标、偏好、实质授权或取舍交回。

完成时在项目既有文档修订过时理由与重评条件。能迁移回本书的经验先匿名重构，保留来源审阅、离线执行与真实运行证据的分别范围。条件没变则复用旧判断；未知没有补齐就保留未知。

这是阅读和任务组织能力，不是自动监控或跨项目选型系统。运行任务单由当前任务授权，`impact-source` 不读取外部项目，也不通知、迁移或执行云端操作。固定 PDF 继续按[出版流程](../docs/publication.md)冻结，不因日常判断更新而自动重出。
